## Slide 2 · 为什么 AI 是 NutriAI 的核心？

```
NutriAI 不是一个普通的 CRUD 管理系统，它让用户和系统之间产生了"对话"

  普通营养 App                                 NutriAI
  ┌─────────────────────────┐        ┌──────────────────────────┐
  │ 用户自己查食物库          │        │ 用户说一段话               │
  │ 手动录入每条营养数据      │   →    │ AI 理解上下文，给出         │
  │ 自己算吃了多少            │        │ 个性化饮食建议 + 食谱       │
  │ 自己决定明天吃什么        │        │ 并记住你的偏好             │
  └─────────────────────────┘        └──────────────────────────┘

本周聚焦三个核心问题：

  ① AI 是怎么"看懂"用户的？      →  提示词工程（Prompt Engineering）
  ② AI 的回答如何变成可交互的界面？ →  双模式输出（JSON 结构化 + Markdown 流式）
  ③ 如何让 AI 越来越"懂"用户？    →  偏好反馈闭环（喜欢/避开 → 下次推荐生效）
```

## Slide 3 · AI 层整体设计 —— 一个接口，多种实现

```
NutriAI 的 AI 层采用了经典的策略模式（Strategy Pattern）

                              用户请求
                                 │
                    ┌────────────▼────────────┐
                    │    NutritionService      │
                    │  （不关心底层用哪个 AI）    │
                    └────────────┬────────────┘
                                 │ 调用统一接口
                    ┌────────────▼────────────┐
                    │      AiService 接口      │  ← 定义契约
                    │  · analyzeAndRecommend() │
                    │  · streamAndRecommend()  │
                    │  · recognizeFood()       │
                    └──────┬──────────┬───────┘
                           │          │
              ┌────────────▼──┐  ┌───▼──────────────┐
              │ OpenAiCompat  │  │  MockAiService    │
              │ (对接 DeepSeek)│  │  (本地模拟)        │
              └───────────────┘  └──────────────────┘

这样设计的好处：
  · 换 AI 供应商 → 改一行配置就行，不用动业务代码
  · 没配 API Key → 自动降级到 Mock，开发调试不受影响
  · 未来接入 GPT / 文心一言 / 通义千问 → 加一个实现类即可
```

## Slide 4 · 提示词是怎么构建的？（上）—— 两套 System Prompt

```
AI 需要被"调教"才知道怎么回答。我们设计了两套指令，分别对应两种使用场景：

场景 A：需要结构化数据（用于展示食谱卡片、营养数值）
  ┌─────────────────────────────────────────────────────────┐
  │  System Prompt 要点：                                    │
  │  "你是资深营养师。必须返回 JSON，包含以下字段："           │
  │                                                         │
  │  {                                                      │
  │    summary           → 营养状况概要                       │
  │    nutritionalAdvice → 每日热量/蛋白/碳水/脂肪建议量       │
  │    recipes[]         → 2-4个食谱（名称/食材/做法/热量）    │
  │    generalTips[]     → 3-5条针对性建议                   │
  │  }                                                      │
  │                                                         │
  │  关键约束：                                              │
  │  · 优先推荐用户所在地区的特色菜                           │
  │  · 避开用户标注的过敏源和忌讳                             │
  │  · 有饮食数据时，必须分析达标情况                          │
  └─────────────────────────────────────────────────────────┘

场景 B：需要自然阅读体验（流式打字机效果）
  ┌─────────────────────────────────────────────────────────┐
  │  System Prompt 要点：                                    │
  │  "请用 Markdown 格式输出，不要输出 JSON"                   │
  │                                                         │
  │  输出结构要求：                                           │
  │  ## 用户健康评估    → BMI、基础代谢                       │
  │  ## 近期饮食分析    → 达标率分析 + 问题指出                │
  │  ## 推荐食谱        → 2-3个，含食材/做法/营养              │
  │  ## 个性化饮食建议  → 3-5条                              │
  │                                                         │
  │  为什么分两套？                                           │
  │  JSON 模式 → 后端解析成对象 → 前端渲染交互卡片（点赞/收藏）  │
  │  Markdown 模式 → 直接流式展示 → 用户边看边等，体验更好      │
  └─────────────────────────────────────────────────────────┘
```

## Slide 5 · 提示词是怎么构建的？（下）—— User Prompt 的动态上下文

```
System Prompt 是"固定剧本"，User Prompt 才是"个性化剧本"

每次调用 AI 前，后端会根据用户数据动态拼装三段上下文：

  ┌─────────────────────────────────────────────────────┐
  │  第一段：用户基础画像（来自 UserProfile）              │
  │  ────────────────────────────────────               │
  │  "男性，25岁，175cm / 70kg                            │
  │   活动量中等，目标增肌，喜欢酱香口味，                  │
  │   所在地区广东广州，偏好鸡胸肉、西兰花，忌讳花生"        │
  └─────────────────────────────────────────────────────┘
                          +
  ┌─────────────────────────────────────────────────────┐
  │  第二段：近期饮食数据（自动聚合最近7天记录）            │
  │  ────────────────────────────────────               │
  │  "近5天日均摄入 1800 kcal · 蛋白 90g · 碳水 200g       │
  │   达标率：热量 90% · 蛋白质 113%⚠️ 超标 · 碳水 80%     │
  │   请根据以上数据分析饮食问题并给出改进建议"             │
  └─────────────────────────────────────────────────────┘
                          +
  ┌─────────────────────────────────────────────────────┐
  │  第三段：饮食偏好（用户标记过喜欢/避开的食物）          │
  │  ────────────────────────────────────               │
  │  "喜欢的食物：鸡胸肉、西兰花、三文鱼                    │
  │   需避开的食物：花生、香菜                             │
  │   推荐时优先喜欢的，避开不喜欢的"                       │
  │                                                     │
  │   ⚠️ 这一段由前端 🧠偏好影响 复选框控制是否注入         │
  └─────────────────────────────────────────────────────┘
                          ↓
           三段合并为一个完整的 User Prompt
                          ↓
              发送给 DeepSeek / Mock AI
```

## Slide 6 · 偏好如何影响 AI 推荐？—— 一个完整的反馈闭环

```
用户的操作 → 如何最终改变 AI 的推荐结果？

  第1步：用户在食谱卡片上点击 👍 喜欢 / 👎 避开
         │
         ▼
  第2步：前端调用 POST /api/food-preference
         保存到数据库 FoodPreference 表
         { userId: 1, foodName: "白切鸡", preference: "LIKE" }
         │
         ▼
  第3步：下次用户请求 AI 推荐时
         NutritionService 调用 buildPreferenceContext(userId)
         │
         ├── 查询该用户所有 LIKE 记录 → 拼成 "喜欢：白切鸡、西兰花..."
         ├── 查询该用户所有 DISLIKE 记录 → 拼成 "避开：花生、香菜..."
         └── 生成提示词文本注入到 User Prompt 末尾
         │
         ▼
  第4步：AI 收到完整的 Prompt → 生成推荐时：
         · 优先推荐白切鸡、西兰花等用户喜欢的食材
         · 自动避开花生、香菜等用户不喜欢的
         │
         ▼
  第5步：用户看到更符合自己口味的推荐 → 继续点赞/避开 → 循环优化

这就是一个典型的"用户反馈 → 数据沉淀 → 提示词注入 → AI 行为改变"的闭环
```

## Slide 7 · AI 食物识别 —— 一句话录入营养数据

```
问题：用户不想一个个手动填热量、蛋白质、碳水、脂肪
解决：让 AI 根据自然语言描述自动识别

  用户输入                  AI 处理                          前端自动填充
  ─────────────────────────────────────────────────────────────────
  "一碗米饭200g            → 识别为午餐                      foodName: 米饭
   + 番茄炒蛋150g"            热量 ~380kcal                   mealType: 午餐
                              蛋白质 ~14g                     calories: 380
                              碳水 ~55g                       protein: 14
                              脂肪 ~10g                       carbs: 55
                              份量 350g                       fat: 10
                                                             servingSize: 350g

技术细节：

  后端 System Prompt 指令：
  "你是营养分析专家。根据食物描述分析营养成分，
   严格返回 JSON：{foodName, mealType, calories, proteinGrams, ...}
   只返回 JSON，不要任何解释"

  参数设置：
  temperature = 0.1      ← 低温度让输出更精确、更稳定
  max_tokens = 300        ← 只需简短 JSON，不需要长回复

  Mock 降级方案：
  没有 API Key 时，用关键词匹配兜底：
  · 描述含"饭"    → 按米饭营养值估算
  · 描述含"肉/鸡" → 按鸡胸肉营养值估算
  · 都不匹配      → 返回通用默认值
```

## Slide 8 · 流式输出 —— 让 AI 的回答"一字一字蹦出来"

```
为什么用流式而不是等全部生成完再显示？

  传统同步模式：                     流式 SSE 模式：
  用户点击 → 等待 5-10 秒           用户点击 → 0.5 秒后开始出字
           → 一下子全出来                    → 像打字机一样逐字显示
           → 体验像"卡住了"                 → 体验像"AI 在思考"


技术实现（前后端配合）：

  后端（Spring WebFlux）                    前端（原生 fetch + ReadableStream）
  ┌────────────────────────┐               ┌──────────────────────────┐
  │ 请求 DeepSeek API       │               │ fetch('/api/recommend/    │
  │ stream: true            │   SSE 数据流   │        stream')          │
  │               ─────────────────────────▶│                          │
  │ 每收到一个 chunk：       │               │ response.body.getReader()│
  │ data: {"choices":       │               │   ↓                      │
  │   [{"delta":{"content": │               │ 逐 chunk 解码 UTF-8       │
  │    "建"}}]}             │               │   ↓                      │
  │   ↓                     │               │ 追加到 DOM 节点           │
  │ extractContent()        │               │   ↓                      │
  │   提取 → "建"           │               │ 滚动条自动跟随            │
  │   ↓                     │               │   ↓                      │
  │ Flux<String> 逐条发出   │               │ 收到 [DONE] → 显示        │
  │                         │               │ [查看结构化食谱] 按钮      │
  │ data: [DONE] → 流结束   │               │                          │
  └────────────────────────┘               └──────────────────────────┘

流式完成后的小彩蛋：
  点击 [📋 查看结构化食谱] → 再调用一次非流式接口
  → 渲染带 👍 👎 ⭐ 按钮的完整食谱卡片
```

## Slide 9 · AI 输出的"防抖"处理 —— JSON 容错解析

```
问题：大模型不是编译器，输出的 JSON 经常有小毛病

  实际收到的 AI 回复                         我们想要的
  ────────────────────────────────         ──────────────────
  "好的，这是为您生成的食谱：                  {                    
  ```json                                   "summary": "...", 
  {                                         "recipes": [...]   
    "summary": "...",                      }                    
    "recipes": [{                                              
      "name": "清蒸鲈鱼",   ← 多余逗号                          
      "ingredients": ["鱼", "姜",], ← 数组末尾多余逗号           
    }],                                                         
  }                                                            
  ```"                                                         

容错三步走：

  Step 1: 提取代码块
          正则匹配 ```json ... ``` ，只要中间的部分

  Step 2: 配对括号
          从第一个 { 开始，手动计数。遇到 { 深度+1，遇到 } 深度-1
          深度归零时就是 JSON 结束位置（处理嵌套结构）

  Step 3: 清理尾部逗号
          正则替换 ,} → }  和  ,] → ]（解决最常见的问题）

  如果以上全失败了怎么办？
  → 不崩溃，把 AI 的原始文本直接作为 summary 展示给用户
  → 至少用户能看到内容，不会白屏
```

  │     ↓                                              │
  │  ④ 根据健康目标调整：                               │
  │     减脂 → 热量 -300   增肌 → 蛋白 1.6g/kg          │
  │     ↓                                              │
  │  ⑤ 根据地区匹配特色菜谱（广东→白切鸡, 四川→水煮鸡片） │

## Slide 13 · 核心技术点回顾

```
NutriAI AI 层的设计思想和关键技术：

  🧠 提示词工程
     两套 System Prompt（结构化 JSON vs 自然 Markdown）

  🔌 策略模式
     AiService 接口 → 一行配置切换 DeepSeek / Mock / 未来任何 AI

  🔄 反馈闭环
     用户喜欢/避开 → 存数据库 → 下次 Prompt 自动引用 → AI 行为改变

  🍲 AI 食物识别
     自然语言 → temperature=0.1 精准 JSON → 自动填表

  🛡️ 容错设计
     JSON 解析三层 fallback + 自动降级 Mock + 网络异常不崩溃
